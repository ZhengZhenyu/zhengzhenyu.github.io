问题很简单：
模型生成的代码，
在哪跑？
AI Agent 不再只是生成文本——它生成代码然后执行。用户说「帮我分析这份数据」，模型吐出一段 Python，这段代码总得有个地方跑。直觉上可以在用户本地、或者扔进 Docker 容器——但两个方案都有严重的安全隐患。
本地执行？ Agent 生成的 curl | bash 直接跑——本机文件、密钥、网络全暴露。已发现多个 Claude Code 相关的安全漏洞（含 CVE 编号）。Anthropic 内部红队测试：无沙箱时，Claude 在 25 次钓鱼攻击中成功泄露凭据 24 次。
Docker？ 设计目标是长运行服务。默认 seccomp（内核级系统调用过滤器）放行 300+ 系统调用。共享内核——一个提权漏洞就能从容器逃逸到宿主机。
Serverless 函数？ 隔离到位，但传统 FaaS 按单次函数调用设计，缺乏完整 Linux 环境的持久性和交互性。

先搞清楚：沙箱到底是什么？

沙箱（Sandbox）就是一个隔离环境。不可信代码在里面随便跑——删文件、装软件、访问网络——都影响不到外面的系统。就像在一个密闭的盒子里做实验，盒子炸了也不影响房间。
Agent 沙箱是沙箱的一个特殊品类：专门为「模型实时生成代码」这个场景设计的。它和传统沙箱（比如浏览器沙箱、手机 App 沙箱）有两个关键区别：
① 生命周期极短：秒级创建，分钟级运行，用完就销毁。不是为长期运行的服务设计的。
② 代码来源完全不可信：代码不是人写的，是模型「编」出来的。同一条 prompt 在不同上下文下可能生成完全不同的代码。无法做代码审查。
实现沙箱的方式有很多种，安全强度也不同——从简单的容器（共享宿主机内核，轻但不够安全），到用户态内核（在应用和内核之间插一层软件拦截），到硬件虚拟化 microVM（独立 Guest 内核，CPU 硬件保证隔离）。
后面展开讲的各种项目（Firecracker、gVisor、E2B）本质上都是在不同的隔离强度、启动速度、部署灵活性之间做取舍，找到自己最适合的场景。

这些问题被拆成了四个独立的关注点

一个用户请求走到代码执行，涉及四个独立的问题。每一层解决一个——下方三层之间是依赖关系（下层为上层提供能力），治理层则是包裹在执行层外面（OpenShell Supervisor 跑在沙箱里，拦截每次操作）。
① Agent 层
生成代码。不负责安全执行。
② 治理运行时
包裹在执行层外面。回答「能做什么」——逐操作策略裁决（Supervisor 跑在沙箱内部）、凭据路由。
③ 执行沙箱
回答「跑在哪」——隔离供给、快照、SDK。治理层的 Supervisor 就运行在这个沙箱里。
④ 隔离层
隔离的具体实现——硬件虚拟化（KVM）还是用户态内核（gVisor）。

为什么非要分层？

一个自然的问题是：为什么不能把所有这些事情塞进一个项目里？答案很简单——因为那四个问题是不同的，硬塞在一起哪个都做不好。
类比一下网络协议栈就清楚了。
物理层（光纤）→ 链路层（Ethernet）→ 网络层（IP）→ 传输层（TCP）→ 应用层（HTTP）。没人会把 TCP 和 HTTP 合并——因为它们解决不同的问题。Agent 沙箱同理（类比，非精确对应）：隔离层类似物理传输层——只负责安全边界；执行层类似路由层——调度和供给；治理层类似流控层——权限和审计。分层让每层独立演进，互不干扰。
业界的实际情况也印证了这个分层——执行沙箱（E2B/Daytona）和治理运行时（OpenShell/MCPGuard）已经被当成两个独立品类在发展了。它们不是竞品，是上下游。

为什么隔离层有这么多选择？

安全、速度、灵活性——不可能三角。每个方案只是在这个三角形里选了一个最适合自己的位置。没有谁比谁更好，只有谁更匹配你的场景约束。
gVisor 的核心壁垒：不需要 KVM（Linux 内核虚拟化模块）。
公有云 VM（EC2、GCE、Azure）默认不暴露 /dev/kvm。gVisor 只需要 seccomp（内核级系统调用过滤器）——Linux 3.5+ 就能跑。这个技术细节是它被 OpenAI、Anthropic、腾讯大规模采用的根本原因。
Firecracker 的取舍：要绝对安全，就得接受 KVM 的约束。
5 个 virtio （虚拟机 I/O 半虚拟化标准接口）设备，最小攻击面。代价是需要裸金属或嵌套虚拟化。在大多数云 VM 里跑不了。

Firecracker · 三线程 + 直通启动 = <125ms

核心设计：三线程分离——API Server 只做配置下发，VMM 线程集中处理所有设备 I/O，vCPU 线程只执行 KVM_RUN ioctl，把 Guest 代码交给 CPU 硬件直接跑。
直通启动：传统 VM 启动要走 BIOS→UEFI→GRUB→模式切换，数百毫秒，固件本身也是攻击面（CVE-2015-3456、CVE-2019-14378）。Firecracker 直接解析 bzImage，读 setup_header，设置 boot_params，跳转到内核入口——省掉整个固件层，时间 + 安全双赢。
# Firecracker 启动 MicroVM（通过 Unix socket 的 HTTP API） curl --unix-socket /run/firecracker.socket -X PUT \ 'http://localhost/boot-source' -H 'Content-Type: application/json' \ -d '{"kernel_image_path":"/srv/vmlinux.bin","boot_args":"console=ttyS0 ro"}'
11 / 27

Firecracker · Jailer 沙箱 + seccomp 过滤 = 纵深防御

Jailer 是独立二进制，在启动 Firecracker 之前先设置好所有 Linux 安全边界——cgroup、namespace、chroot、seccomp-bpf、capabilities——全部就位后才 exec Firecracker。「先隔离，后启动」确保即使 Firecracker 代码有未知漏洞，攻击者也受严格限制。
为什么 300+ → 10 是 Firecracker 的安全核心？
Docker 默认暴露 300+ 系统调用给容器——每个都是潜在攻击入口。Firecracker 按线程角色安装不同严格程度的 seccomp 过滤器：API ~40、VMM ~30（仅 KVM 相关 ioctl）、vCPU ~10（仅 KVM_RUN）。攻击者即使控制了 vCPU 线程，也只能调用 10 个 syscall——读文件、发网络请求这些操作根本无法执行。
对比 gVisor：Sentry 自身暴露 ~55 个 syscall 给宿主机。两者思路一致——最小化宿主机可见的攻击面——但实现路径不同：FC 靠硬件 + seccomp，gVisor 靠用户态内核 + seccomp。

gVisor · 一次 syscall 怎么被拦截

Sentry + Gofer 决策/执行分离是 gVisor 最精巧的设计。Sentry 知道文件系统层级和权限模型——但不持有宿主机文件描述符。需要文件时请 Gofer 打开，Gofer 通过 Unix socket 的 SCM_RIGHTS 把 fd 传过来。即使 Sentry 被攻破，攻击者也碰不到宿主机文件。
GPU (nvproxy)、Netstack (用户态 TCP/IP)：宿主机内核只看到以太网帧，看不到 TCP 连接状态和 payload。nvproxy 支持 T4/A100/L4/H100，多沙箱共享 GPU。
兼容性约束：syscall 覆盖 ~82%（~200+/340），io_uring 默认禁用。腾讯在 10 个代码执行数据集上做了 74,379 次 runsc vs runc 对比测试，修正后正确率仅差 0.13 个百分点。但不确定时先跑测试。

envd——沙箱里的 PID 1
每个 E2B 沙箱启动后，envd 作为 init 运行。所有文件读写、进程执行、环境变量注入都通过它。通过 vsock（KVM 宿主机-Guest 专用通信通道，不经过网络栈）和 Orchestrator 通信。MMDS Token 双端认证——Orchestrator 启动前把一次性 Token 写入 MMDS（MicroVM Metadata Service），envd 启动后读取，SDK 连接时比对。memguard 用 mlock() 锁住 API Key 防 swap 泄漏——但环境变量在沙箱内仍然可见，这是为什么需要 OpenShell 凭据代理。

三种安全思路，解决的是不同层面的问题

硬件隔离
Firecracker · Kata Containers
KVM 独立内核。边界由 CPU 硬件保证——Intel VT-x / AMD-V。优势：安全边界硬，不依赖沙箱内进程协作。代价：需 KVM，公有云 VM 默认不支持。沙箱内行为无可见性。
软件隔离
gVisor
用户态内核 Sentry 拦截 syscall。宿主机暴露从 300+ 压缩到 ~55 个。优势：不需要 KVM——任意 Linux 都能跑。代价：延迟 ~2.2x native。Sentry 是 Go 代码，有 bug 就是攻击面。
策略治理
OpenShell(用户态Supervisor) · MCPGuard(内核eBPF)
不提供隔离——在已有隔离之上逐操作裁决。优势：动态策略热加载。凭据代理不落沙箱。代价：依赖 Supervisor 正常运转。非独立安全层。
三者是互补关系。硬件隔离防代码逃逸到宿主机。软件隔离收缩内核攻击面——300+ syscall 压到 55 个。策略治理管逻辑权限——防 Agent 访问不该访问的目标。理想方案把三者叠起来，缺一层就有盲区。

训练场景——RL 为什么要求更高

RL Agent 的探索性行为必然包含危险操作——这不是 bug，是机制。策略为了最大化 reward 会尝试一切路径。训练场景对沙箱的要求比推理高一个数量级。
真实案例：腾讯 × MiniMax（2026.03）
腾讯云 Agent Runtime 沙箱支撑 MiniMax 的 RL 框架 Forge，每日运行百万级 gVisor 沙箱。74,379 次 runsc vs runc 对比测试，修正后正确率仅差 0.13 个百分点。58 秒内启动 3 万个 4C8G 沙箱实例，单镜像每分钟创建 60 万沙箱。冷启动 80ms 级（快照恢复），P99 延迟 <1s。原生兼容 E2B 协议。
真实案例：OpenAI RL 基础设施演进
OpenAI 在 2026 年公开分享了其 RL 训练沙箱的演进路径：fork-exec → Linux 容器 → gVisor → 硬件虚拟化 MicroVM（Cloud Hypervisor / CrosVM）。使用增量块级快照（XFS + copy-on-write）+ 快照感知调度路由，支撑 Agent 任务运行 3 天以上。
RL 训练的四个特殊需求：① 高并发 rollout——每训练步数千沙箱 ② 快照/恢复——MCTS 减少 40-64% token ③ 环境状态持久化——脏环境污染 reward ④ 严格租户隔离——共享环境破坏马尔可夫假设。
选型：对抗性探索 → Firecracker/Kata · 受限环境 → gVisor · 模型评估 → 容器+seccomp

三种产品三种方案：Claude.ai（Web）用 ephemeral gVisor 容器；Claude Code（本地）用 Seatbelt/Bubblewrap OS 沙箱，权限提示减少 84%；Claude Cowork（桌面）用完整本地 VM。Anthropic 2026.05 发布详细 Containment 文档——核心原则是用环境控制设硬边界，而非仅依赖模型层面的安全策略。

生态里还有这些值得关注的项目

MCPGuard-Dynamic (Meta, 2026.07)：eBPF 内核级拦截。BPF LSM 在 open/connect/execve 拦截。论文报告攻击阻止率 68.9%，延迟仅 +0.488ms。威胁模型：MCP 服务器自身不可信。
Monty（Pydantic 开源）：Rust 实现的沙箱化 Python 运行时。启动 4.5μs，快照仅数 KB。默认零权限。适合仅需 Python 的轻量场景。

Cloud Hypervisor：与 FC 同源（crosvm）。GPU 直通、Windows、热迁移。多厂商治理。Koyeb 2025 年从 FC 迁过来——因为 GPU。
趋势：安全哲学在趋同——「默认零权限，显式授权」成为共识，不管实现方式是 eBPF、WASM、MicroVM 还是自定义解释器。

选型——先搞清楚你的约束

Q1: 有 /dev/kvm 吗？
没有 → gVisor（只需 seccomp）。有 → Q2。
Q2: 要硬件级安全？
是 → Firecracker / Kata。否但需完整 Linux → gVisor
Q3: 要平台能力？（SDK/模板/快照/合规）
是 → E2B 或 Daytona。否 → 直接用隔离层。
Q4: 要 GPU？
是 → gVisor (nvproxy) 或 Kata+GPU。否 → 都行。
快速对照
K8s 升级安全 → Kata
创业从零搭 → E2B
大规模 RL+GPU → gVisor
金融最高合规 → Firecracker BYOC
云 VM 无 KVM → gVisor
MCP 加固 → eBPF · 仅 Python → Monty
原则：先列约束，再定位——选最匹配的，不是最强的。

总结

1
Agent 沙箱是一个新品类。为「模型生成代码」设计的轻量隔离环境。四层架构：隔离层（怎么隔离）→ 执行层（跑在哪）→ 治理层（能做什么）→ Agent 层（做什么）。
2
分层是为了让每个问题可解。隔离、执行、治理、Agent 是四个不同的问题。硬塞一起哪个都做不好。类比网络协议栈——物理/链路/网络/传输/应用各管各的。
3
没有银弹。安全、速度、灵活性的不可能三角意味着不存在最好的方案。gVisor 不需要 KVM 是结构性壁垒，Firecracker 硬件隔离是安全上限，OpenShell 策略治理弥补可见性短板。
4
「盒子 + 规则」是正确方向。物理隔离（Firecracker）+ 策略治理（OpenShell）+ 凭据保护 = 纵深防御。缺一环就有盲区。
