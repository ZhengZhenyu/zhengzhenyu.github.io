问题很简单：
模型生成的代码，
在哪跑？
AI Agent 不再只是生成文本——它生成代码然后执行。用户说「帮我分析这份数据」，模型吐出一段 Python，这段代码总得有个地方跑。直觉上可以在用户本地、或者扔进 Docker 容器——但两个方案都有严重的安全隐患。
本地执行？ Agent 生成的 curl | bash 直接跑——本机文件、密钥、网络全暴露。已发现多个 Claude Code 相关的安全漏洞（含 CVE 编号）。Anthropic 内部红队测试：无沙箱时，Claude 在 25 次钓鱼攻击中成功泄露凭据 24 次。（来源：Anthropic 2025 安全公开报告）
Docker？ 设计目标是长运行服务。默认 seccomp（内核级系统调用过滤器）放行 300+ 系统调用。共享内核——一个提权漏洞就能从容器逃逸到宿主机。
Serverless 函数？ 隔离到位，但传统 FaaS 按单次函数调用设计，缺乏完整 Linux 环境的持久性和交互性。

先搞清楚：沙箱到底是什么？

沙箱（Sandbox）就是一个隔离环境。不可信代码在里面随便跑——删文件、装软件、访问网络——都影响不到外面的系统。就像在一个密闭的盒子里做实验，盒子炸了也不影响房间。
Agent 沙箱是沙箱的一个特殊品类：专门为「模型实时生成代码」这个场景设计的。它和传统沙箱（比如浏览器沙箱、手机 App 沙箱）有两个关键区别：
① 生命周期极短：秒级创建，分钟级运行，用完就销毁。不是为长期运行的服务设计的。
② 代码来源完全不可信：代码不是人写的，是模型「编」出来的。同一条 prompt 在不同上下文下可能生成完全不同的代码。无法做代码审查。
实现沙箱的方式有很多种，安全强度也不同——从简单的容器（共享宿主机内核，轻但不够安全），到用户态内核（在应用和内核之间插一层软件拦截），到硬件虚拟化 microVM（独立 Guest 内核，CPU 硬件保证隔离）。
后面展开讲的各种项目（Firecracker、gVisor、E2B）本质上都是在不同的隔离强度、启动速度、部署灵活性之间做取舍，找到自己最适合的场景。

这些问题被拆成了四个独立的关注点

一个用户请求走到代码执行，涉及四个独立的问题。每一层解决一个——下方三层之间是依赖关系（下层为上层提供能力），治理层则是包裹在执行层外面（OpenShell Supervisor 跑在沙箱里，拦截每次操作）。
① Agent 层
生成代码。不负责安全执行。
② 治理运行时
包裹在执行层外面。回答「能做什么」——逐操作策略裁决（Supervisor 跑在沙箱内部）、凭据路由。
③ 执行沙箱
回答「跑在哪」——隔离供给、快照、SDK。治理层的 Supervisor 就运行在这个沙箱里。
④ 隔离层
隔离的具体实现——硬件虚拟化（KVM）还是用户态内核（gVisor）。

为什么非要分层？

一个自然的问题是：为什么不能把所有这些事情塞进一个项目里？答案很简单——因为那四个问题是不同的，硬塞在一起哪个都做不好。
类比网络协议栈：
物理层→链路层→网络层→传输层→应用层，没人会合并 TCP 和 HTTP。Agent 沙箱同理：隔离层=安全边界，执行层=调度供给，治理层=权限审计。分层让每层独立演进。
业界的实际情况也印证了这个分层——执行沙箱（E2B/Daytona）和治理运行时（OpenShell/MCPGuard）已经被当成两个独立品类在发展了。它们不是竞品，是上下游。

为什么隔离层有这么多选择？

安全、速度、灵活性——不可能三角。每个方案只是在这个三角形里选了一个最适合自己的位置。没有谁比谁更好，只有谁更匹配你的场景约束。
gVisor 的核心壁垒：不需要 KVM（Linux 内核虚拟化模块）。
公有云 VM（EC2、GCE、Azure）默认不暴露 /dev/kvm。gVisor 只需要 seccomp（内核级系统调用过滤器）——Linux 3.5+ 就能跑。这个技术细节是它被 OpenAI、Anthropic、腾讯大规模采用的根本原因。
Firecracker 的取舍：要绝对安全，就得接受 KVM 的约束。
5 个 virtio （虚拟机 I/O 半虚拟化标准接口）设备，最小攻击面。代价是需要裸金属或嵌套虚拟化。在大多数云 VM 里跑不了。

训练场景——RL 为什么要求更高

有了前面的技术地基，现在看具体场景怎么选。先看最苛刻的 RL 训练——它对沙箱的要求比推理高一个数量级。
RL Agent 的探索性行为必然包含危险操作——这不是 bug，是机制。策略为了最大化 reward 会尝试一切路径。训练场景对沙箱的要求比推理高一个数量级。
真实案例：腾讯 × MiniMax（2026.03）
腾讯云 Agent Runtime 沙箱支撑 MiniMax 的 RL 框架 Forge，每日运行百万级沙箱（CubeSandbox, RustVMM+KVM 自研）。58 秒内启动 3 万个 4C8G 沙箱实例，单镜像每分钟创建 60 万沙箱。冷启动 80ms 级（快照恢复），P99 延迟 <1s。原生兼容 E2B 协议。（来源：腾讯云公开技术博客，2026.03）
真实案例：OpenAI RL 基础设施演进
OpenAI 在 2026 年公开分享了其 RL 训练沙箱的演进路径：fork-exec → Linux 容器 → gVisor → 硬件虚拟化 MicroVM（Cloud Hypervisor / CrosVM）。使用增量块级快照（XFS + copy-on-write）+ 快照感知调度路由，支撑 Agent 任务运行 3 天以上。（来源：OpenAI 工程博客，2026）
RL 训练的四个特殊需求：① 高并发 rollout——每训练步数千沙箱 ② 快照/恢复——MCTS 减少 40-64% token ③ 环境状态持久化——脏环境污染 reward ④ 严格租户隔离——共享环境破坏马尔可夫假设。
选型：对抗性探索 → Firecracker/Kata · 受限环境 → gVisor · 模型评估 → 容器+seccomp

Firecracker · 三线程架构 + 直通启动 = <125ms

核心设计：三线程分离——API Server 只做配置下发，VMM 线程集中处理所有设备 I/O，vCPU 线程只执行 KVM_RUN ioctl，把 Guest 代码交给 CPU 硬件直接跑。I/O 不阻塞 Guest 计算。
直通启动：传统 VM 启动要走 BIOS→UEFI→GRUB→模式切换，数百毫秒，固件本身也是攻击面。Firecracker 直接解析 bzImage，读 setup_header，设置 boot_params，跳转到内核入口——省掉整个固件层，时间 + 安全双赢。
上图底部 Jailer 沙箱在 Firecracker 启动前已就绪——cgroup、namespace、seccomp-bpf、chroot、特权降级全部就位后才 exec Firecracker。详情见下一页。
15 / 31

Firecracker · Jailer 沙箱 + seccomp 过滤 = 纵深防御

Jailer 是独立二进制，在启动 Firecracker 之前先设置好所有 Linux 安全边界——cgroup、namespace、chroot、seccomp-bpf、capabilities——全部就位后才 exec Firecracker。「先隔离，后启动」确保即使 Firecracker 代码有未知漏洞，攻击者也受严格限制。
为什么 300+ → 10 是 Firecracker 的安全核心？
Docker 默认暴露 300+ 系统调用给容器——每个都是潜在攻击入口。Firecracker 按线程角色安装不同严格程度的 seccomp 过滤器：API ~40、VMM ~30（仅 KVM 相关 ioctl）、vCPU ~10（仅 KVM_RUN）。攻击者即使控制了 vCPU 线程，也只能调用 10 个 syscall——读文件、发网络请求这些操作根本无法执行。
对比 gVisor：Sentry 自身暴露 ~55 个 syscall 给宿主机。两者思路一致——最小化宿主机可见的攻击面——但实现路径不同：FC 靠硬件 + seccomp，gVisor 靠用户态内核 + seccomp。

gVisor · 一次 syscall 怎么被拦截

Sentry + Gofer 决策/执行分离是 gVisor 最精巧的设计。Sentry 知道文件系统层级和权限模型——但不持有宿主机文件描述符。需要文件时请 Gofer 打开，Gofer 通过 Unix socket 的 SCM_RIGHTS 把 fd 传过来。即使 Sentry 被攻破，攻击者也碰不到宿主机文件。
GPU (nvproxy)、Netstack (用户态 TCP/IP)：宿主机内核只看到以太网帧，看不到 TCP 连接状态和 payload。nvproxy 支持 T4/A100/L4/H100，多沙箱共享 GPU。
性能与兼容性：systrap 默认 ~2.2x 延迟 vs runc（KVM 模式 ~1.8x，ptrace 已废弃）。文件 I/O（Gofer 代理）open+O_CREAT 延迟最高 48x runc，内部 tmpfs 大请求吞吐反超 runc。syscall 兼容 ~82%，io_uring 默认禁用。x86_64 支持跳板优化（替换 syscall 指令为 jmp 绕过 seccomp），ARM64 不支持。

四个关键机制
① envd 守护进程 —— 沙箱的「操作系统」
每个沙箱启动后 envd 作为 PID 1 运行，负责：
· 命令执行——接收 SDK 发来的指令，fork 子进程，流式回传 stdout/stderr
· 文件读写——沙箱内文件系统的读写代理
· 进程管理——后台进程的 PID 追踪、信号发送、退出码收集
② vsock 通信 —— 绕过网络栈
envd 和 Orchestrator 之间不走 TCP/IP，而是通过 KVM 的 virtio-vsock（宿主机-Guest 专用通道）。不经过网络栈意味着：零网络配置、零防火墙规则、零中间人风险。
③ MMDS Token 双端认证
Orchestrator 在启动 Firecracker 前把一次性 Token 写入 MMDS（MicroVM Metadata Service，AWS 设计的云实例元数据服务）。envd 启动后读取 MMDS 中的 Token，SDK 连接时比对——两端分别持有 Token 的一半，中间人无法伪造。沙箱销毁后 Token 自动失效。
④ memguard 密钥保护
用户 API Key 通过 mlock() 锁定在物理内存中，禁止被 swap 到磁盘。但环境变量在沙箱内仍然可见——恶意代码可以用 env 命令读取。这是为什么需要 OpenShell 凭据路由器——API Key 不注入沙箱，请求到达代理时才附加。

项目拆解 · 治理运行时层

OpenShell —— Gateway 管策略，Supervisor 管执行

NVIDIA + Cisco 在 GTC 2026 联合发布，Apache 2.0。它不做隔离——它定义策略。架构上分为控制平面（Gateway，跑在宿主机）和数据平面（Supervisor，跑在每个沙箱内部），两者通过 gRPC 长连接通信。策略热加载、凭据不落沙箱、每次操作有审计记录。
四层纵深防御
① 文件系统 · Landlock LSM，声明式路径白名单，内核强制
② 网络 · OPA 策略引擎，TOFU+Per-binary 身份，热加载
③ 进程 · seccomp BPF，syscall 白名单过滤，静态策略
④ 推理路由 · inference.local 透明代理，凭证自动注入
攻击路径示例：恶意代码 → Landlock 阻断文件读写 → OPA 阻断异常网络 → seccomp 阻断危险 syscall → inference.local 阻断凭据泄露。每一层堵一个出口。
关键架构选择：Supervisor 主动向 Gateway 发起出站 gRPC 连接——不依赖容器编排层的网络配置（Pod IP、端口映射、NAT）。这意味着同一套策略逻辑可以在 Docker、K8s、MicroVM 等多种后端上一致工作。

三种安全思路，解决的是不同层面的问题

硬件隔离
Firecracker · Kata Containers
KVM 独立内核。边界由 CPU 硬件保证——Intel VT-x / AMD-V。优势：安全边界硬，不依赖沙箱内进程协作。代价：需 KVM，公有云 VM 默认不支持。沙箱内行为无可见性。
软件隔离
gVisor
用户态内核 Sentry 拦截 syscall。宿主机暴露从 300+ 压缩到 ~55 个。优势：不需要 KVM——任意 Linux 都能跑。代价：延迟 ~2.2x native。Sentry 是 Go 代码，有 bug 就是攻击面。
策略治理
OpenShell(用户态Supervisor) · MCPGuard(内核eBPF)
不提供隔离——在已有隔离之上逐操作裁决。优势：动态策略热加载。凭据代理不落沙箱。代价：依赖 Supervisor 正常运转。非独立安全层。
三者是互补关系。硬件隔离防代码逃逸到宿主机。软件隔离收缩内核攻击面——300+ syscall 压到 55 个。策略治理管逻辑权限——防 Agent 访问不该访问的目标。理想方案把三者叠起来，缺一层就有盲区。

Firecracker 还是 gVisor？——技术选型的核心逻辑

为什么有人选 Firecracker
E2B、AWS Lambda、Fly.io 的选择——硬件隔离是刚需。场景：多租户运行完全不可信的 AI 生成代码。KVM 独立内核，CPU 硬件保证边界。5 个 virtio 设备，攻击面最小化。
代价：需要裸金属或嵌套虚拟化。公有云 VM（EC2、GCE、Azure）默认不暴露 /dev/kvm。Firecracker 没有 PCI 总线——架构上不可能支持 GPU 直通。
E2B 的后端选型：用 Nomad 而非 K8s——因为 Firecracker 不是容器，Nomad 的 system job + 原始进程执行更适配节点本地 VM 池管理模式。Go 全栈（Firecracker Go SDK + Nomad + Consul 原生）。
为什么有人选 gVisor
OpenAI、Anthropic、Google Cloud Run 的选择——没有 /dev/kvm。跑在标准云 VM 上，容器原生 K8s 集成。Sentry 用户态内核拦截 syscall，宿主机仅暴露 ~55 个。
代价：syscall 兼容 ~82%，文件 I/O 延迟可达 runc 的 48x。Go GC 对延迟敏感负载有影响。Sentry 是 Go 代码——有 bug 就是攻击面。
独特优势：nvproxy 支持 GPU（T4/A100/L4/H100），多沙箱共享。腾讯 Agentic-RL 每日数百万沙箱——GPU + 规模 + 低成本是硬需求。
决策树：需要 GPU？→ gVisor(nvproxy) 或 Cloud Hypervisor(VFIO)。有 /dev/kvm？→ Firecracker（硬件隔离，最小攻击面）。跑在云 VM 上？→ gVisor（无需 KVM）。K8s 最强隔离？→ Kata Containers。Firecracker 和 gVisor 不是替代关系——是在不同基础设施约束下的最优解。

选型——先搞清楚你的约束

Q1: 有 /dev/kvm 吗？
没有 → gVisor（只需 seccomp）。有 → Q2。
Q2: 要硬件级安全？
是 → Firecracker / Kata。否但需完整 Linux → gVisor
Q3: 要平台能力？（SDK/模板/快照/合规）
是 → E2B 或 Daytona。否 → 直接用隔离层。
Q4: 要 GPU？
是 → gVisor (nvproxy) 或 Kata+GPU。否 → 都行。
快速对照
K8s 升级安全 → Kata
创业从零搭 → E2B
大规模 RL+GPU → gVisor
金融最高合规 → Firecracker BYOC
云 VM 无 KVM → gVisor
MCP 加固 → eBPF · 仅 Python → Monty
原则：先列约束，再定位——选最匹配的，不是最强的。

生态里还有这些值得关注的项目

MCPGuard-Dynamic (Meta, 2026.07)：eBPF 内核级拦截。BPF LSM 在 open/connect/execve 拦截。论文报告攻击阻止率 68.9%，延迟仅 +0.488ms。威胁模型：MCP 服务器自身不可信。（来源：Meta AI 论文，2026）
Monty（Pydantic 开源）：Rust 实现的沙箱化 Python 运行时。启动 4.5μs，快照仅数 KB。默认零权限。适合仅需 Python 的轻量场景。
Kata Containers：K8s RuntimeClass。支持 FC/Cloud Hypervisor/QEMU 后端。已有 K8s 的团队升级安全的最短路径。
Cloud Hypervisor：与 FC 同源（crosvm）。GPU 直通、Windows、热迁移。多厂商治理。Koyeb 2025 年从 FC 迁过来——因为 GPU。
趋势：安全哲学在趋同——「默认零权限，显式授权」成为共识，不管实现方式是 eBPF、WASM、MicroVM 还是自定义解释器。

总结

1
Agent 沙箱是一个新品类。为「模型生成代码」设计的轻量隔离环境。四层架构：隔离层（怎么隔离）→ 执行层（跑在哪）→ 治理层（能做什么）→ Agent 层（做什么）。
2
分层是为了让每个问题可解。隔离、执行、治理、Agent 是四个不同的问题。硬塞一起哪个都做不好。类比网络协议栈——物理/链路/网络/传输/应用各管各的。
3
没有银弹。安全、速度、灵活性的不可能三角意味着不存在最好的方案。gVisor 不需要 KVM 是结构性壁垒，Firecracker 硬件隔离是安全上限，OpenShell 策略治理弥补可见性短板。
4
「盒子 + 规则」是正确方向。物理隔离（Firecracker）+ 策略治理（OpenShell）+ 凭据保护 = 纵深防御。缺一环就有盲区。
一句话：Agent 沙箱的本质不是选一个工具，
是四层各司其职——隔离层做边界、执行层做供给、治理层做裁决。
