# 技术项目洞察 · 风格补充

> 基础规范见 `../blog-common/base-style.md`。本文档仅描述「技术项目洞察」品类特有的要求。

## 品类定义

聚焦**具体开源项目或技术产品**的深度分析。从源码、架构、社区等维度去拆解一个项目，并分析其背后的战略逻辑和行业位置。

标杆文章：`source/_posts/nvidia-openshell-insight.md`

## 文章结构模式

```
1. 引言（宏观趋势 → 具体问题 → 引出分析对象）
2. 为什么需要 X（问题/需求背景）
3. 行业/生态全景（将对象放入坐标，不是孤立介绍）
4. 深度分析（核心章节，2-3节）
   ├── 项目概览（仓库、版本、社区数据 → stats-grid）
   ├── 架构全景（分层图 → arch-grid 或 stack-diagram）
   ├── 关键机制（逐层拆解 → phase-card + 代码示例）
   └── 可选：特色设计（如形式化验证、自主提案）
5. 竞品对比（品类差异 → table-wrap）
6. 战略分析（商业逻辑、生态布局）
7. 风险与局限性
8. 结语（趋势判断）
```

## 独特要求

- [ ] 项目基本信息表（仓库、版本、许可、语言、社区数据）
- [ ] 架构分层图（arch-grid 或 stack-diagram）
- [ ] ≥2 处源码/配置级代码示例
- [ ] 竞品/替代方案对比表（≥5 对比维度）
- [ ] 战略/商业逻辑分析（对于公司驱动的项目）
- [ ] 生态合作方/采用方表格（如有）
- [ ] 项目风险分析（非吹捧，保持客观）
- [ ] 结语必须包含趋势判断

## 数据要求

- 项目元数据：Stars、Forks、Contributors、Releases、最近发布频率
- 所有数据标注时间点
- 对比表中的数据统一口径（如都取某个时间点）
- **数据来源优先级**：官方文档 > 项目源码/Release Notes > 一手采访/官方博客 > 第三方 benchmark
- **必须从官方来源核实**：定价、版本号、性能指标、API 字段名——这四类不可依赖第三方来源
- 官方数据与第三方数据冲突时，以官方为准，可注明「官方数据为 X，第三方 benchmark 通常为 Y」

## 视觉元素侧重点

- `arch-grid` + `arch-card`：架构分层（必备）
- `stack-diagram`：技术栈位置图
- `stats-grid`：项目关键指标
- `table-wrap`：项目信息、竞品对比、生态合作方
- `verdict`：核心矛盾、战略意图、品类关系
- `callout`：攻击向量、方案对比
- `phase-card`：关键机制详解
- `policy-flow`：闭环流程
- `workflow`：有序检查步骤

## 语言风格

- 保持技术分析的冷静克制
- 分析而非评论——给证据不给观点
- 长句用于解释机制，短句用于总结判断
- 允许适度的战略推测，但标注推断依据
