# 技术项目洞察 · 写作工作流

## 触发方式

```
/blog-insight <主题> [选项]
```

示例：
```
/blog-insight Kubernetes 1.32 新特性深度分析 --repo https://github.com/kubernetes/kubernetes
/blog-insight 从 WasmEdge 看 WebAssembly 服务端现状 --focus 架构,安全
```

可选参数：
- `--focus 架构,安全` — 重点研究方向
- `--repo https://github.com/xxx/xxx` — 开源项目仓库
- `--refs url1,url2` — 已有参考链接

## 参考文件

| 文件 | 用途 |
|------|------|
| `.claude/skills/blog-common/base-style.md` | 通用规范（Frontmatter、CSS变量、暗色模式、HTML组件） |
| `.claude/skills/blog-insight/style-guide.md` | 品类特有要求（结构、深度标准、视觉侧重点） |
| `source/_posts/nvidia-openshell-insight.md` | 标杆文章 |

## 五阶段流程

```
Phase 1 ────▶ Phase 1.5 ──▶ Phase 2 ────▶ Phase 3 ────▶ Phase 4 ────▶ Phase 5
研究(3并行)   数据核实(1)   大纲(1)      初稿(1)      打磨(3并行)   终审(1)
```

---

## 数据准确性原则（贯穿全流程）

> **最高优先级规则**：所有技术数据必须优先采用官方文档、源码或一手来源。第三方 benchmark、技术博客、竞品对比文章仅作交叉参照，不可作为最终数据源。

- 官方文档 > 项目源码/Release Notes > 一手采访/官方博客 > 第三方 benchmark
- 第三方数据与官方数据冲突时，以官方为准，并在文中注明「官方数据为 X，第三方 benchmark 通常为 Y」
- 定价、版本号、性能指标、API 字段名——这四类数据**必须**从官方来源核实

---

## Phase 1: 多角度并行研究

> 研究中如涉及项目官方文档（`--repo` 参数指定或 Agent 自行发现），**必须通过 WebFetch 或 curl 抓取官方文档页面**进行核实，不可仅依赖第三方来源。

启动 3 个独立 Agent 并行执行：

### Agent 1: 技术深度研究

```
你是资深技术分析师。请对「{主题}」进行深度技术研究。{如有 --focus，加上：重点研究：{--focus}}。{如有 --repo，加上：请通过 WebFetch 获取该仓库的 README、架构文档、最近 Release Notes。分析 Stars、Contributors、提交频率、技术栈、许可证等关键元数据。}

研究要求：
1. 核心技术架构：组件、分层、数据流
2. 关键机制/算法：不是功能介绍，而是它如何实现的
3. 技术决策的 trade-off：为什么选 A 不选 B
4. 版本与社区：最新版本号、发布时间、Stars、Contributors、许可证
5. 源码级细节：配置示例、API 设计、关键代码结构

每个论断需要具体依据（版本号、数字、引用），不要空泛描述。
{如有 --refs，加上：已提供的参考链接：{--refs}}
```

### Agent 2: 战略/行业背景研究

```
你是科技行业分析师。请对「{主题}」进行战略与行业背景分析。

分析要求：
1. 为什么出现在这个时间点？行业背景和推动力是什么？
2. 背后的商业/战略逻辑（公司驱动的话，它图什么？）
3. 它解决了什么以前没解决好的问题？
4. 目标用户和场景
5. 行业趋势：短期热点还是长期方向？
6. 风险与不确定性

区分「事实」和「推断」。每个判断要有逻辑链条。
```

### Agent 3: 竞品全景研究

```
你是竞品分析师。请对「{主题}」进行竞品和替代方案全景分析。

分析要求：
1. 直接竞品：谁在做类似的事？定位和差异？
2. 替代方案：不用这个，用户现在用什么？
3. 对比维度：技术路线、社区规模、商业支持、适用场景
4. 品类定义：主角属于什么品类？竞品是否属于同一品类？

输出竞品对比矩阵。每个竞品需包含：名称、一句话定位、核心差异点。
```

---

## Phase 1.5: 数据核实

> 此阶段是**必执行步骤**。三份研究报告完成后，必须先用一个 Agent 对关键数据点做交叉验证，再进入大纲设计。

```
你是数据核实员。请对以下三份研究报告中的关键数据进行逐一核实。

核实原则：官方文档 > 项目源码/Release Notes > 一手采访/官方博客 > 第三方 benchmark。第三方数据与官方数据冲突时以官方为准。

## 必须核实的四类数据
1. **定价与计划**：抓取官方定价页面，确认价格、免费额度、各 plan 限制
2. **性能指标**：冷启动时间、内存开销、并发上限——必须以官方文档或源码为准
3. **API/配置字段名**：模板配置、SDK 方法名、参数名——必须与实际 API 一致
4. **功能特性**：是否支持某功能（fork、GPU、持久化等）——必须以官方文档为准，不可仅凭第三方 benchmark 推断

## 研究报告
[Phase 1 的三份报告全文]

## 输出格式
以「修正清单」形式输出：
- [数据点] 当前值 → 修正值 → 来源（URL）
- 无问题则标注「已核实，无误」
```

## Phase 2: 内容架构设计

```
你是资深技术内容架构师。基于三份研究报告，为「{主题}」设计详细大纲。

先阅读通用规范、风格补充和标杆文章，校准质量标准。

## 研究报告
[Phase 1 的三份报告全文]

## 大纲要求

1. **章节结构**（6-8个大节），按品类标准结构组织：
   引言 → 为什么需要 → 行业全景(可选) → 深度分析(2-3节核心) → 竞品对比 → 战略分析 → 风险/局限性 → 结语

2. **每节标注**：
   - 核心论点（一句话）
   - 关键数据和引用来源
   - 适合的视觉元素类型（arch-grid / table-wrap / verdict / callout / phase-card / stats-grid 等）
   - 估计字数

3. **逻辑检查**：每节之间的递进关系是什么？是否存在断裂？
```

---

## Phase 3: 撰写初稿

```
你是资深技术作家。基于大纲撰写完整博客初稿。

先阅读通用规范、风格补充和标杆文章，校准风格。

## 大纲
[Phase 2 大纲]

## 研究报告
[Phase 1 三份报告全文]

## 写作要求

1. **语言**：中文为主，技术术语保留英文。先判断再展开。对比用「不是...而是...」。
   分析克制——给证据不给观点。长句解释机制，短句总结判断。

2. **视觉元素**（写入实际的 HTML+CSS，每个元素后跟 <style> 标签）：
   - 架构分层 → arch-grid + arch-card（必备）
   - 技术栈位置 → stack-diagram
   - 项目指标 → stats-grid + stat-card
   - 对比数据 → table-wrap > table
   - 核心判断 → verdict
   - 列举要点 → callout
   - 机制详解 → phase-card
   - 闭环流程 → policy-flow
   - 有序步骤 → workflow
   - 每个元素必须提供 :root[data-theme="dark"] 适配
   - CSS 使用主题变量：--border, --radius, --surface, --text, --text-muted, --text-soft, --bg, --primary, --shadow-sm, --font-mono

3. **深度硬指标**：
   - 项目基本信息表（仓库、版本、许可、语言、社区数据）
   - ≥2 处源码/配置代码块（指定语言）
   - 竞品对比表（≥5 对比维度）
   - 局限性/风险分析章节
   - 战略/商业逻辑分析
   - 结语的趋势判断
   - 所有数据有具体数字和时间标注
   - 无"很多""大量""众多"等模糊词

输出完整的 Markdown 文件。不要解释，直接输出文章。
```

## Phase 4: 并行打磨（3 Agent）

### Agent 4a: 风格一致性检查

```
你是严格的技术编辑。对照通用规范、风格补充和标杆文章，检查初稿。

检查维度：
1. 品类要求的章节结构是否完整
2. 深度硬指标是否全部满足（统计清单）
3. 语言风格是否匹配品类要求
4. 模糊描述替换建议（每个 → 具体数字）
5. 数据时间标注缺失
6. 逻辑递进是否有断裂

输出修改建议列表。需要重写的段落给出完整内容。
```

### Agent 4b: 视觉元素增强

```
你是技术博客视觉设计师。检查初稿的视觉元素是否充分。

参考品类风格补充中的视觉侧重点。

检查要点：
1. 哪些内容适合但尚未使用视觉元素？
2. 哪些现有元素可以增强？
3. 每处建议给出完整 HTML+CSS（含 dark mode 适配）

输出格式：「在哪插入什么元素」+ 完整 HTML+CSS 代码。
```

### Agent 4c: 暗色模式验证

```
你是前端工程师。检查初稿中所有自定义 CSS 的暗色模式适配。

检查要点：
1. 找出所有硬编码颜色（#xxx, rgb(), rgba()）
2. 确认每个彩色元素都有 :root[data-theme="dark"] 规则
3. 暗色模式对比度检查（正文 ≥4.5:1）
4. 渐变色在暗色模式下是否合适

输出格式：[行号] 问题 → 缺失的完整 dark mode CSS 规则
```

## Phase 5: 终审合成

```
你是资深技术博客主编。基于初稿和三份打磨报告，生成最终版。

先阅读通用规范、风格补充和标杆文章校准质量标准。

## 初稿
[Phase 3 初稿]

## 风格审查
[Agent 4a 报告]

## 视觉增强
[Agent 4b 报告]

## 暗色模式
[Agent 4c 报告]

## 终稿要求
1. 应用所有打磨建议
2. 每处视觉元素包含完整 HTML + CSS + dark mode 适配
3. Frontmatter 最终确认
4. 全文逻辑连贯，数据准确

输出完整的 Markdown 文件，从 Frontmatter 到最后一个字符。不要输出任何解释性文字。
```

将终稿写入 `source/_posts/<slug>.md`。Slug 根据标题提取英文关键词用 `-` 连接。

告知用户文件路径和文章概要。
