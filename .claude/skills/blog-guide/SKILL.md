# 操作经验总结 · 写作工作流

## 触发方式

```
/blog-guide <主题> [选项]
```

示例：
```
/blog-guide VS Code 中高效使用 Claude Code 的十条经验 --tool "Claude Code"
/blog-guide Hexo 博客从搭建到部署全流程 --focus 配置,部署
```

可选参数：
- `--tool <工具名>` — 主角工具/平台名称
- `--focus 配置,性能` — 重点关注的方面
- `--refs url1,url2` — 已有参考链接

## 参考文件

| 文件 | 用途 |
|------|------|
| `.claude/skills/blog-common/base-style.md` | 通用规范（Frontmatter、CSS变量、暗色模式、HTML组件） |
| `.claude/skills/blog-guide/style-guide.md` | 品类特有要求（结构、深度标准、视觉侧重点） |
| `source/_posts/claude-memory-insight.md` | 标杆文章 A（偏概念+经验） |
| `source/_posts/claude-code-configuration-guide.md` | 标杆文章 B（偏配置+实操） |

## 五阶段流程

```
Phase 1 ────▶ Phase 1.5 ──▶ Phase 2 ────▶ Phase 3 ────▶ Phase 4 ────▶ Phase 5
研究(3并行)   数据核实(1)   大纲(1)      初稿(1)      打磨(3并行)   终审(1)
```

> 流程结构和 blog-insight 一致，但每个阶段的 Agent 职责和研究维度不同。

---

## 数据准确性原则（贯穿全流程）

> **最高优先级规则**：所有技术数据必须优先采用官方文档或一手来源。

- 官方文档 > 工具源码/Release Notes > 官方博客 > 社区经验
- 配置参数名、版本号、兼容性范围、定价——**必须**从官方来源核实
- 第三方经验与官方文档冲突时以官方为准

## Phase 1: 多角度并行研究

### Agent 1: 工具机制研究

```
你是开发者工具专家。请对「{主题}」中的核心工具/平台进行机制层面的研究。{如有 --tool，加上：主角工具：{--tool}}。

研究要求：
1. 核心功能和工作原理（不是罗列功能，是解释机制）
2. 配置体系：配置文件位置、格式、关键参数、优先级/作用域
3. 常见使用模式和工作流
4. 版本差异和兼容性（不同 OS、不同版本的差异）
5. 官方文档中的最佳实践和反模式

每个要点标注信息来源（官方文档/社区/个人经验）。
{如有 --refs，参考：{--refs}}
```

### Agent 2: 最佳实践与社区经验收集

```
你是技术社区研究员。请收集「{主题}」相关的社区最佳实践和使用经验。

收集要求：
1. 社区公认的最佳实践（≥5 条）
2. 高频踩坑点（≥3 个）和解决方案
3. 知名项目/团队的用法参考（如 PyTorch 的 CLAUDE.md 配置）
4. 不同场景下的推荐用法差异（个人开发 vs 团队协作 vs 企业部署）
5. 常见误区：大家以为对的但实际上不推荐的做法

搜索中英文社区（GitHub、官方论坛、博客、Reddit、知乎等）。
每一条标注来源和适用条件（什么场景下适用）。
```

### Agent 3: 竞品/替代方案对比

```
你是工具对比分析师。请对「{主题}」涉及的工具进行竞品和替代方案分析。

分析要求：
1. 同类工具/方案有哪些？（至少列出 3 个）
2. 每个替代方案的定位差异
3. 核心对比维度：上手难度、功能完整度、社区活跃度、文档质量、性能
4. 什么场景下选哪个？（决策树式的建议）

输出对比表。不要求像洞察类那么深度——侧重实用性，帮助读者做选择。
```

## Phase 1.5: 数据核实

> 此阶段是**必执行步骤**。重点核实配置参数、版本号、兼容性范围和定价。

```
你是数据核实员。请对研究报告中的关键数据进行核实。

核实原则：官方文档 > 工具源码/Release Notes > 官方博客 > 社区经验。
重点检查：
1. 配置文件字段名是否与实际 API 一致（如参数名、枚举值、路径）
2. 版本号和兼容性范围（OS 支持、SDK 版本范围）
3. 定价和计划信息（免费额度、限制条件）
4. 社区经验中的命令/代码是否可直接运行

输出「修正清单」，无问题则标注「已核实」。
```

---

## Phase 2: 内容架构设计

```
你是技术内容架构师。基于三份研究报告，为「{主题}」设计详细大纲。

先阅读通用规范、风格补充和标杆文章 A/B，校准质量标准。

## 研究报告
[Phase 1 的三份报告全文]

## 大纲要求

1. **章节结构**（5-7个大节），按品类标准结构组织：
   引入(个人场景) → 价值说明 → 核心概念 → 实操指南(2-3节核心) → 最佳实践案例(可选) → Tips/Checklist → 总结+学习路径 → 参考资料

2. **每节标注**：
   - 核心要点（一句话）
   - 需要的代码/配置示例
   - 适合的视觉元素（table-wrap / callout / phase-card / code-block）
   - 估计字数

3. **实操章节设计**：
   - 从简单到复杂的渐进式结构
   - 每个操作步骤标注：前置条件 → 操作 → 预期结果 → 常见问题
   - Good vs Bad 对比的插入点
```

## Phase 3: 撰写初稿

```
你是资深技术作家。基于大纲撰写完整博客初稿。

先阅读通用规范、风格补充和标杆文章 A/B，校准风格。

## 大纲
[Phase 2 大纲]

## 研究报告
[Phase 1 三份报告全文]

## 写作要求

1. **语言**：中文为主，技术术语保留英文。口语化程度适中，允许第一人称。
   先讲「什么时候用」再讲「怎么用」。善用类比降低理解门槛。
   允许主观评价但要有依据。经验教训要写清前因后果（场景→问题→解决）。

2. **视觉元素**（写入完整 HTML+CSS，含 dark mode）：
   - 配置/对比 → table-wrap > table（高频）
   - 操作步骤 → phase-card
   - 注意事项 → callout
   - 关键提示 → verdict
   - 数据卡片 → stats-grid（如有）
   - **不使用** arch-grid、stack-diagram、policy-flow
   - 每个元素后跟 <style> 标签，含 :root[data-theme="dark"] 适配

3. **内容硬指标**：
   - 开篇有个人使用场景或动机
   - ≥3 处可运行的完整代码/配置示例
   - ≥1 处 Good vs Bad 对比
   - ≥3 条实用 Tips
   - 总结中包含渐进式学习路径建议
   - 参考资料列表（URL 链接）
   - 配置标注作用域（全局/项目/个人）
   - 版本号标注兼容性范围
   - 路径标注操作系统差异

输出完整的 Markdown 文件。不要解释，直接输出文章。
```

---

## Phase 4: 并行打磨（3 Agent）

### Agent 4a: 风格一致性检查

```
你是严格的技术编辑。对照通用规范、风格补充和标杆文章 A/B，检查初稿。

检查维度：
1. 品类要求的章节结构是否完整
2. 内容硬指标是否全部满足（统计清单）
3. 语言风格是否匹配品类要求（口语化适中、第一人称适度、善用类比）
4. 操作步骤是否具备可复现性（读者能照着做吗？）
5. 版本和 OS 兼容性是否标注清楚
6. Good vs Bad 对比是否有足够说服力

输出修改建议列表。需要重写的段落给出完整内容。
```

### Agent 4b: 视觉元素增强

```
你是技术博客视觉设计师。检查初稿的视觉元素是否充分。

参考品类风格补充中的视觉侧重点。注意：此类不使用 arch-grid、stack-diagram、policy-flow。

检查要点：
1. 哪些内容适合但尚未使用视觉元素？（配置项→表格、操作步骤→phase-card、注意事项→callout）
2. 代码块是否指定语言？是否有足够注释说明？
3. 每处建议给出完整 HTML+CSS（含 dark mode 适配）
```

### Agent 4c: 暗色模式 + 可用性验证

```
你是前端工程师。检查初稿中所有自定义 CSS 的暗色模式适配 + 代码示例的可复现性。

检查要点：
1. 所有硬编码颜色是否有 dark mode 适配
2. 代码块中的命令是否可直接复制执行（无多余空格、无省略号）
3. 路径是否同时标注 macOS/Linux/Windows 差异
4. 配置文件是否完整（非片段）

输出格式：[行号] 问题 → 修复方案
```

---

## Phase 5: 终审合成

```
你是资深技术博客主编。基于初稿和三份打磨报告，生成最终版。

先阅读通用规范、风格补充和标杆文章校准质量标准。

## 初稿
[Phase 3 初稿]

## 风格审查
[Agent 4a 报告]

## 视觉增强
[Agent 4b 报告]

## 验证报告
[Agent 4c 报告]

## 终稿要求
1. 应用所有打磨建议
2. 每处视觉元素包含完整 HTML + CSS + dark mode 适配
3. Frontmatter 最终确认
4. 所有代码/命令可直接复制执行

**关键**：这篇文章的核心价值是「读者能照着做」。每个操作步骤必须可复现。

输出完整的 Markdown 文件，从 Frontmatter 到最后一个字符。不要输出任何解释性文字。
```

将终稿写入 `source/_posts/<slug>.md`。Slug 根据标题提取英文关键词用 `-` 连接。

告知用户文件路径和文章概要。
