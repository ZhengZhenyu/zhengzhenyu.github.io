# 业界趋势洞察 · 写作工作流

## 触发方式

```
/blog-trend <主题> [选项]
```

示例：
```
/blog-trend 2026 年 AI Agent 从工具到平台的范式转移
/blog-trend 开源 LLM 与闭源模型的差距正在缩小吗 --focus 技术,商业
```

可选参数：
- `--focus 技术,商业,政策` — 重点分析维度
- `--refs url1,url2` — 已有参考链接/报告

| 文件 | 用途 |

## 五阶段流程

```
Phase 1 ────▶ Phase 1.5 ──▶ Phase 2 ────▶ Phase 3 ────▶ Phase 4 ────▶ Phase 5
研究(4并行)   数据核实(1)   大纲(1)      初稿(1)      打磨(3并行)   终审(1)
```

---

## 数据准确性原则（贯穿全流程）

> **最高优先级规则**：市场数据、统计数据、预测数据必须标注来源和时间。不可混用不同口径的数据。

- 一手数据（公司财报、官方报告）> 权威二手数据（Gartner、IDC）> 行业媒体
- **标注规则**：确定数据标注「来源+时间」、估算数据标注「估算+来源+时间」、预测数据标注「预测+来源+时间」
- 不同来源数据冲突时，在文中同时呈现并加以说明

---

> 研究阶段比其他品类多一个 Agent——趋势类需要更多维度的信息输入。

## Phase 1: 多角度并行研究（4 Agent）

### Agent 1: 现状与数据收集

```
你是行业数据分析师。请对「{主题}」进行现状全景扫描和数据收集。

研究要求：
1. 市场规模和增速（最近的报告数据，标注来源和时间）
2. 关键玩家和市场份额（至少列出前 5 名）
3. 近期重大事件时间线（过去 12-18 个月的关键节点）
4. 投资/融资趋势（如果相关）
5. 采用率数据（开发者调查、企业采用报告等）

每项数据必须标注来源和时间。优先使用一手数据（公司财报、官方报告），其次使用权威二手数据（Gartner、IDC、Statista）。
区分「确定数据」「估算数据」「预测数据」。
{如有 --refs，参考：{--refs}}
```

### Agent 2: 驱动力分析

```
你是科技产业分析师。请对「{主题}」进行驱动力分析。

分析要求：
1. 技术驱动力：什么技术突破使这个趋势成为可能？（具体的技术、论文、产品）
2. 商业驱动力：谁在推动？他们为什么现在推动？（市场机会、竞争压力、商业模式创新）
3. 政策/合规驱动力：监管在推动还是阻碍？（具体法规名称和影响）
4. 用户/需求驱动力：用户行为或需求发生了什么变化？

{如有 --focus，重点分析指定的维度}

每个驱动力需回答三个问题：
- 它是什么？（具体描述）
- 它为什么现在起作用？（而不是一年前或一年后）
- 它的持续性如何？（短期脉冲 / 中期趋势 / 长期结构性变化）
```

### Agent 3: 多方观点收集

```
你是科技评论分析员。请收集「{主题}」相关的多方观点和立场分析。

收集要求：
1. 乐观派观点：谁在说好？他们的逻辑和依据是什么？
2. 质疑/悲观派：谁在唱衰？他们的论据是什么？
3. 中立/实用派：谁在说「看情况」？条件是什么？
4. 利益分析：每个人的立场和利益关系是什么？（为什么他这么说？）

搜索来源：行业报告、技术博客、高管访谈、财报电话会、学术论文、社交媒体上的关键意见领袖。

每个观点标注：谁说的、什么时候说的、他们的利益立场是什么。
不要只是罗列观点——分析每个观点背后的逻辑链条和假设。哪些假设是可验证的？
```

### Agent 4: 历史类比与参照

```
你是科技史研究者。请为「{主题}」寻找历史参照系。

研究要求：
1. 历史上是否有类似的技术趋势或范式转移？（至少找 1-2 个类比）
2. 当时的演进路径是怎样的？（关键节点、转折点、赢家和输家）
3. 哪些条件促成了当时的成功/失败？
4. 当前趋势与历史类比的关键相似点和不同点
5. 从历史中可迁移的经验教训

类比不追求完美匹配，但需要解释为什么选择这个类比、以及其局限性。
类比本身不是判断——它是帮助读者理解复杂趋势的框架。
```

## Phase 1.5: 数据核实

> 趋势类文章最怕「假数据撑真判断」。此阶段聚焦数据溯源和口径校验。

```
你是数据核实员。请对研究报告中的关键数据进行溯源核实。

核实重点：
1. 市场规模/增速数据——标注来源、时间、是「实际数据」还是「预测」
2. 融资/投资数据——确认金额、轮次、时间、领投方
3. 采用率/渗透率数据——确认统计口径（调查样本量、定义）
4. 时间线数据——交叉验证事件日期

对每个数据点标注：
- 来源 URL
- 数据性质：确定 / 估算 / 预测
- 时效性：截至日期
- 与其他来源的一致性

输出「数据溯源报告」。有冲突的数据标注多重来源并提供判断。
```

## Phase 2: 内容架构设计

```
你是资深科技评论撰稿人。基于四份研究报告，为「{主题}」设计详细大纲。

先阅读通用规范和风格补充，校准质量标准。

## 研究报告
[Phase 1 的四份报告全文]

## 大纲要求

1. **章节结构**（6-8个大节），按品类标准结构组织：
   引言(信号+核心判断) → 现状全景 → 驱动力分析 → 关键变量/不确定性 → 多方观点 → 趋势预判(核心) → 从业者建议 → 结语(一句话收束)

2. **每节标注**：
   - 核心论点（一句话，趋势类的论点是概率性的）
   - 支撑数据和来源
   - 适合的视觉元素（verdict / callout / stats-grid / table-wrap / phase-card）
   - 估计字数

3. **趋势预判章节设计**（最核心）：
   - 短期（1-2年）+ 中期（3-5年）
   - 每个预判标注置信度（高/中/低）
   - 可能触发转折的关键事件
   - 备选场景（如果 X 不发生，可能走 Y 路线）

4. **逻辑检查**：
   - 数据是否支撑判断？
   - 是否有反方观点的诚实呈现？
   - 预判的边界条件是否清晰？
```

## Phase 3: 撰写初稿

```
你是资深科技评论撰稿人。基于大纲撰写完整博客初稿。

先阅读通用规范和风格补充，校准风格。

## 大纲
[Phase 2 大纲]

## 研究报告
[Phase 1 四份报告全文]

## 写作要求

1. **语言**：冷静、克制、留余地。
   趋势判断讲概率不讲绝对。
   多用「可能」「倾向于」「值得关注的是」而非「必然」「一定」。
   区分三层：事实陈述 / 数据引用 / 个人判断。
   核心判断必须用短句。长句展开分析脉络。
   允许使用比喻来简化复杂格局。
   中文为主，行业术语和机构名保留原文。

2. **视觉元素**（写入完整 HTML+CSS，含 dark mode）：
   - 核心判断/预判 → verdict（高频）
   - 多方观点/变量罗列 → callout
   - 市场数据 → stats-grid
   - 格局/时间线/建议 → table-wrap
   - 驱动力展开 → phase-card
   - **不使用** arch-grid、stack-diagram、policy-flow
   - 每个元素后跟 <style> 标签，含 :root[data-theme="dark"] 适配

3. **内容硬指标**：
   - 开篇给出核心判断（一句话，加粗）
   - ≥3 个独立数据源
   - 驱动力分析覆盖≥2 个维度（技术/商业/政策/用户）
   - 呈现对立观点或不确定性
   - 趋势预判标注时间范围（短期/中期）和置信度
   - 不同角色的差异化建议
   - 后续值得关注的信号列表
   - 所有数据标注来源和时间，预测标注「预测」标签

输出完整的 Markdown 文件。不要解释，直接输出文章。
```

## Phase 4: 并行打磨（3 Agent）

### Agent 4a: 风格与逻辑检查

```
你是严格的科技编辑。对照通用规范、风格补充，检查初稿。

检查维度：
1. 核心判断是否在开头给出
2. 趋势预判是否标注了时间范围和置信度
3. 是否有对立观点的诚实呈现
4. 数据来源是否标注清楚
5. 是否区分了「事实」「预测」「个人判断」
6. 语言是否留有余地（趋势类最忌讳武断）
7. 逻辑链条：数据 → 分析 → 判断，是否连贯
8. 比喻是否恰当，有没有过度简化

输出修改建议列表。
```

### Agent 4b: 视觉元素增强

```
你是技术博客视觉设计师。检查初稿的视觉元素。

参考品类风格补充——趋势类侧重 verdict、callout、stats-grid、table-wrap。
不使用 arch-grid、stack-diagram、policy-flow。

检查要点：
1. 核心判断是否用了 verdict 突出
2. 市场数据是否用 stats-grid 呈现
3. 对比/时间线是否用 table-wrap
4. 每处建议给出完整 HTML+CSS（含 dark mode）
```

### Agent 4c: 暗色模式 + 数据标注验证

```
你是前端工程师 + 事实核查员。检查：

1. 所有自定义 CSS 的暗色模式适配
2. 所有数据是否有来源标注
3. 所有预测是否标注「预测」标签
4. 所有 URL 链接是否可访问

输出格式：[行号] 问题 → 修复方案
```

## Phase 5: 终审合成

```
你是资深科技评论主编。基于初稿和三份打磨报告，生成最终版。

先阅读通用规范和风格补充校准质量标准。

## 初稿
[Phase 3 初稿]

## 风格审查
[Agent 4a 报告]

## 视觉增强
[Agent 4b 报告]

## 验证报告
[Agent 4c 报告]

## 终稿要求
1. 应用所有打磨建议
2. 趋势预判标注置信度和时间范围
3. 数据标注来源，预测标注标签
4. 语言克制，留有余地
5. Frontmatter 最终确认

**关键**：趋势类的核心价值是「帮助读者理解复杂格局和可能走向」,不是「给出确定答案」。
保持诚实——不确定就说不确定。

输出完整的 Markdown 文件，从 Frontmatter 到最后一个字符。不要输出任何解释性文字。
```

## 最终输出

将终稿写入 `source/_posts/<slug>.md`。Slug 根据标题提取英文关键词用 `-` 连接。

告知用户文件路径、文章概要和关键判断摘要。

## 首次使用后建议

此类目前尚无标杆文章。建议：
1. 第一次使用时选一个中等复杂度的话题试跑
2. 产出后挑一篇满意的作为后续标杆
3. 将标杆路径更新到品类风格补充的「标杆文章」字段
4. 根据实际效果迭代调整各阶段 Agent 的 prompt
